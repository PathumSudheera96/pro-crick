PRO-CRICK — CODEX EXECUTION STEPS
===================================

Purpose
-------
This file contains the recommended Codex execution sequence for the Pro-Crick project.

Project stack:
- Next.js
- Payload CMS
- PostgreSQL
- TypeScript
- Tailwind CSS
- pnpm
- GitHub
- Docker Compose for standard local development
- cPanel production hosting
- Local persistent storage for normal images/PDFs in V1
- YouTube/Vimeo embeds for videos

IMPORTANT WORKFLOW RULE
-----------------------
Do NOT give Codex this entire file and ask it to execute everything at once.

Use ONE numbered step at a time.

Recommended workflow for every step:

1. Make sure AGENTS.md exists in the repository root.
2. Open a new Codex task/branch.
3. Copy ONE prompt from this document.
4. Let Codex inspect the repository before editing.
5. Review the implementation plan if requested.
6. Let Codex implement only that step.
7. Review the diff.
8. Run/check:
   - pnpm lint
   - pnpm typecheck
   - pnpm test (if available)
   - pnpm build
9. Fix issues before moving to the next step.
10. Commit/merge the completed step.
11. Start the next step on the updated codebase.

Do not continue to a later stage while the current stage has known build, migration,
security, or data-model problems.

STEP 01 — INITIAL PROJECT BOOTSTRAP
======================================================================

Goal:
Create the initial working Next.js + Payload application.

Prompt:

Read AGENTS.md before making changes.

Implement STEP 01 only: initial project bootstrap.

Requirements:

- Use Next.js App Router.
- Use TypeScript.
- Use Payload CMS.
- Use PostgreSQL.
- Use pnpm.
- Use Tailwind CSS.
- Keep Payload CMS and the public frontend in the same Next.js application.
- Configure PostgreSQL using environment variables.
- Docker Compose must be the standard local development environment.
- Create `compose.yaml` with `app` and `db` services.
- Create `Dockerfile.dev`.
- Create `.dockerignore`.
- Configure a pinned PostgreSQL image and database health check.
- Use a persistent named volume for PostgreSQL development data.
- Configure a documented persistent local upload path/volume.
- Use bind-mounted source code for development/hot reload.
- Do not depend on host `node_modules`.
- Do not put secrets directly in Compose files.
- Create a safe .env.example with placeholders only.
- Do not commit secrets.
- Establish a clean folder structure consistent with AGENTS.md.
- Add basic README development instructions if they do not already exist.
- Do NOT implement Players, Pages, taxonomies, enquiries, applications, or public site features yet.

The main success criteria are:

- `docker compose up --build` can start the local stack
- the `db` service becomes healthy
- the app connects to PostgreSQL using the Docker service hostname
- development server can start
- Payload loads
- /admin can be reached
- PostgreSQL data persists after a normal container restart
- local uploads use the documented persistent development path
- TypeScript is valid
- production build succeeds

Before editing:
1. Inspect the current repository.
2. State the implementation plan.

After implementation:
1. Run available lint/typecheck/build commands.
2. Review your own diff.
3. List all files created or changed.
4. List required environment variables.
5. Document exact fresh-clone Docker commands in `docs/DEVELOPMENT_SETUP.md`.
6. Update `CONTRIBUTING.md` if collaboration/setup behavior changed.
7. Report any unresolved setup issues.
